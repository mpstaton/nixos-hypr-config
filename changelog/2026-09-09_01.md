# Enabled Is Not Running: Two Silent Gaming Failures

## Why Care?

Three days ago [gaming came back to this laptop](2026-09-06_01.md) in one
deletable file. It worked. It was also, in two separate ways, quietly not
working — and neither way announced itself.

The Steam client kept dropping into HTML render errors: panes of the interface
replaced by the browser equivalent of a shrug. Games ran, but sluggishly. Both
symptoms have the same shape, and it's a shape worth naming because NixOS makes
it especially easy to hit:

**A setting can be `true` in your configuration and still not be true on your
machine.** Once because you wrote the fix and never built it. Once because the
thing you enabled lives outside the sandbox that needed it.

Neither failure produced an error a person would see. One produced no error at
all — just a framerate that was never as high as it should have been, which is
the hardest class of bug there is, because nothing is wrong except the number
you never saw.

## What's New?

- **Steam's UI stopped glitching.** The `nixpkgs.overlay` patching Steam's
  desktop file — written days ago, sitting uncommitted and unbuilt — is now
  actually on the system. Generation 27 → 28.
- **GameMode works for the first time.** One line, `programs.steam.package`
  with `extraLibraries`, puts `libgamemode.so` inside Steam's FHS sandbox for
  both architectures. The daemon had been running this whole time with nothing
  able to call it. **The speed difference is immediately noticeable.**
- **`extest`'s alarming error spam was investigated and deliberately left
  alone.** It is not a bug. Details below, because the next person to read
  those logs will also assume it is.

## The Story

The report was "Steam shows html render errors." The config looked fine. The
config *was* fine. Here is what the machine actually said.

### One: a fix that existed only as prose

`git status` showed `hosts/hypr-nix/gaming.nix` modified. Inside was a fifty
line comment block, correct in every particular, explaining that Steam's
`.desktop` file ships two keys —

```ini
PrefersNonDefaultGPU=true
X-KDE-RunOnDiscreteGpu=true
```

— which politely ask the launcher to start Steam on the discrete GPU, and that
launchers grant this the only way the freedesktop spec knows how: by exporting
`DRI_PRIME=1`. On a Mesa-only PRIME laptop that's correct and harmless. On this
one it is neither, because the 4070 is driven by the proprietary NVIDIA driver
that Mesa cannot render on directly. The comment even had the measurements:

| Environment | What actually renders |
|---|---|
| *(nothing set)* | Mesa Intel(R) Graphics (RPL-S) — iGPU, native |
| `DRI_PRIME=1` | **zink** — OpenGL-on-Vulkan, on the proprietary driver |
| `nvidia-offload` | NVIDIA GeForce RTX 4070 Laptop — dGPU, native |

Steam's entire interface is Chromium. Chromium-on-zink-on-proprietary-NVIDIA-on-XWayland
crashes its GPU process, and when Chromium's renderer dies it draws you the sad
tab. That's the "HTML render error."

The diagnosis was right. It had simply never been built. And this is the part
worth writing down: **the running Steam process could be asked directly.**

```console
$ tr '\0' '\n' < /proc/2987/environ | grep DRI_PRIME
DRI_PRIME=1

$ ps -o lstart= -p 2987
Mon Sep  7 11:27:43 2026
```

Two days old, carrying the exact variable the comment predicted, launched from
a `.desktop` file that still read `true` because no `nixos-rebuild` had ever
run. A comment describing a fix has the same effect on your GPU as no comment
at all.

The logs agreed, in three different files:

```
webhelper.txt   Error: AcquirePixmap: failed to create glx pixmap for window
                X Error of failed request: GLXBadPixmap
cef_log.txt     GPU process exited unexpectedly: exit_code=139   (×8)
                Terminating renderer for bad IPC message, reason 213
                WARNING:sad_tab.cc(255)] Tab Killed:
```

### Two: a daemon with nobody to answer the phone

While reading `console-linux.txt` for the render bug, a different line kept
scrolling past:

```
gamemodeauto: dlopen failed - libgamemode.so: cannot open shared object file
```

`programs.gamemode.enable = true` has been set since the module was written.
`gamemoded` was genuinely running. Both the 32- and 64-bit libraries were
genuinely in the store. And every single request still failed, because Steam
runs inside an FHS sandbox whose `/usr/lib` contains **only what the module was
told to put there** — and nobody had told it about GameMode.

So the CPU governor never switched to performance. Priorities were never
raised. Nothing errored, nothing warned, and the only symptom was a framerate
nobody had a baseline for.

The fix is one line, and the shape of it is the interesting bit:

```nix
programs.steam.package = pkgs.steam.override {
  extraLibraries = p: [ p.gamemode.lib ];
};
```

`extraLibraries` feeds `multiPkgs`, and the FHS builder calls it **twice — once
per architecture, with the matching nixpkgs set**. So `p.gamemode.lib` resolves
to the 64-bit library for games and the i686 one for the 32-bit Steam client,
from a single expression. No `pkgsi686Linux` incantation, no duplicated list.

## Under the Hood

### The verification that looked like a failure

Checking the built sandbox for the library appeared to show it half-working:

```console
$ ls $rootfs/usr/lib/libgamemode*
MISSING
$ ls $rootfs/usr/lib32/libgamemode*
libgamemode.so -> ...gamemode-1.8.2-lib/lib/libgamemode.so
```

32-bit landed, 64-bit didn't. Except it had. `/usr/lib` inside that rootfs is a
symlink to `/usr/lib64` — an **absolute** symlink, which resolves against the
real filesystem root when you poke at it from outside the sandbox, and
therefore resolves to nothing:

```
rootfs/lib      -> /usr/lib
rootfs/usr/lib  -> /usr/lib64      # absolute; dangling from the outside
rootfs/usr/lib32/    ← real directory
rootfs/usr/lib64/    ← real directory
```

`find` for the filename rather than `ls` on the assumed path showed both copies
present. Worth remembering when inspecting any `buildFHSEnv` output: **check
the paths you were given, not the paths you expected.**

### The red herring, left in place on purpose

These scroll past constantly and look like the smoking gun:

```
ERROR: ld.so: object '/nix/store/...-extest-1.0.2/lib/libextest.so'
       from LD_PRELOAD cannot be preloaded (wrong ELF class: ELFCLASS32): ignored
```

Nothing is broken. `programs.steam.extest.enable` sets `LD_PRELOAD` to
`pkgs.pkgsi686Linux.extest` — 32-bit, chosen deliberately by the module,
because the Steam binary it needs to hook is 32-bit. Steam's main process loads
it fine. The 64-bit helpers see an architecture mismatch, log, and carry on.
Any single-arch `LD_PRELOAD` produces this on a multi-arch process tree.

There is no version of this that doesn't log. "Fixing" it means disabling
working Wayland controller remapping to quiet a line. Left alone, and now
documented so the next reader doesn't spend an hour on it.

### Before and after

Counters taken from the same log files across the restart. They are frozen, not
reset — that's zero new events, not a cleared slate.

| Signal | Before | After restart |
|---|---|---|
| GPU process crashes | 10 | **0 new** |
| `AcquirePixmap` / GLXBadPixmap | 7 | **0 new** |
| `sad_tab` / Tab Killed | present | **none** |
| `gamemodeauto: dlopen failed` | every startup | **none** |
| `DRI_PRIME` in Steam's environment | `1` | **unset** |

## What's Next

The honest caveat on the render fix: Steam was restarted from a shell that had
no `DRI_PRIME` set, so a clean result proves the *pipeline* is healthy but not
that the *launcher* stopped injecting the variable. The system `.desktop` now
reads `false` and there's no override shadowing it in
`~/.local/share/applications/`, so the remaining risk is a launcher serving a
cached entry. One command settles it after any normal launch:

```bash
tr '\0' '\n' < /proc/$(pgrep -x steam)/environ | grep DRI_PRIME
```

Silence means fixed.

The broader lesson is cheap to state and apparently expensive to learn: this
repo is good at documenting *why* a setting exists, and that documentation is
worth nothing until `nixos-rebuild switch` runs. A comment is not a
configuration. Generation numbers are the only thing that tells the truth.

Worth auditing whether anything else in `gaming.nix` is enabled-but-unreachable
in the same way GameMode was. `mangohud` and `gamescope` are both invoked
explicitly per game rather than dlopen'd, so they're probably fine — but
"probably fine" is exactly what GameMode was for three days.
