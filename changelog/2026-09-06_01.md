# Steam on NixOS, and the 32-bit Stack Nobody Tells You About

## Why Care?

This machine used to run Garuda Linux, where installing Steam was `pacman -S
steam` and it simply worked. On NixOS the same intent takes a file — and if you
write that file the obvious way, Steam opens to a black window and tells you
nothing about why.

That gap is the interesting part. Arch had already put a **32-bit graphics
stack** on the machine, globally, via its multilib repo. Steam's client is a
32-bit program. So is a lot of what it runs. NixOS declines to guess, which
means the thing Garuda gave you for free is the exact thing you have to ask
for by name — and the failure when you don't looks like a broken app, not a
missing dependency.

Everything needed now lives in `hosts/hypr-nix/gaming.nix`, wired in by one
line. Delete the line and the desktop is precisely what it was before. That
property is the point: gaming is a want, not an architecture decision, and it
shouldn't leave residue in a machine that is a workstation first.

## What's New?

- **`hosts/hypr-nix/gaming.nix`** — Steam (the NixOS *module*, not the bare
  package), GE-Proton, protontricks, extest, gamemode, gamescope, mangohud, and
  the 32-bit graphics and audio stacks.
- **32-bit audio moved to where it's needed.** `configuration.nix` had
  `alsa.support32Bit` deliberately off with a comment explaining the cost.
  It's now switched on by `gaming.nix` instead, so removing that import
  reverts it with no edit anywhere else.
- **`python3`, `bc` and `file`** added to `systemPackages` — unrelated to
  gaming, and explained below.
- **README** gained a Gaming section, and the repo gained this `changelog/`.
- **flake bump** — nixpkgs `b18a4b9` → `6713828`, plus home-manager,
  zen-browser and hunk. Generation 26 is built and booted from it.

## The Story

The migration off Garuda has been a long exercise in finding the things that
distro did quietly. Steam turned out to be three of them stacked.

**One: the module versus the package.** `environment.systemPackages = [
pkgs.steam ]` produces a binary that will not run. Steam is a proprietary blob
that expects an ordinary FHS filesystem — `/usr/lib`, `/lib32`, the works — and
NixOS has no such thing. It also needs udev rules to see a controller and
firewall holes to reach the network. `programs.steam.enable` wires all of that;
the package alone wires none of it.

**Two: 32-bit graphics.** `hardware.graphics.enable = true` covers 64-bit only.
The client, most older native Linux games, and every 32-bit Windows game run
through Proton all need a 32-bit Mesa/Vulkan/libGL to draw a single pixel.
Without `enable32Bit`, Steam either refuses to launch or opens black. This is
*the* most common "Steam is broken on NixOS" cause, and it produces no message
that points at it.

**Three: 32-bit audio, which fails differently and worse.** The game launches.
It renders. It is completely silent. Nothing errors.

```
hardware.graphics.enable       →  64-bit only  →  Steam won't start
hardware.graphics.enable32Bit  →  the client draws
services.pipewire.alsa.support32Bit  →  the game makes noise
```

That last line has a price, and it was already written down in this repo before
any of this work: it drags i686 builds of the audio stack into every nixpkgs
bump, and Hydra's i686 coverage is thin enough that some of those miss
`cache.nixos.org` and compile locally. An earlier commit turned it *off* for
exactly that reason, on the grounds that nothing here needed it. Now something
does. Rather than flip the flag in place and orphan the comment, the setting
moved next to the thing that justifies it — which is also what makes the module
cleanly deletable.

### The one that isn't NixOS's fault

This is a System76 Serval with an RTX 4070 running in PRIME **offload** mode:
the Intel iGPU drives the panel, the NVIDIA card sleeps until something is
explicitly launched onto it. Great for battery, and it's why Hyprland is stable
here. It also means:

> A game launched normally from Steam renders on the Intel iGPU. It runs, it
> runs badly, and nothing tells you why.

The fix is per game, in Launch Options:

```
nvidia-offload gamemoderun mangohud %command%
```

`nvidia-offload` already existed on the system, from
`prime.offload.enableOffloadCmd`. mangohud earns its place here specifically
because its overlay *names the rendering GPU* — it's how you confirm the
offload took, without alt-tabbing to `nvidia-smi`.

This is the one machine-specific thing in the file, and it is deliberately
**prose, not configuration**. On a single-GPU machine the section doesn't
apply and the rest still works.

### The setting that everyone tells you to turn on

`programs.gamescope.capSysNice` is off, on purpose, and the file says why at
length so nobody "fixes" it later. Setting it lets gamescope raise its own
scheduling priority — and with native Steam it breaks the exact use case you
wanted, because the setcap'd binary refuses Steam's `LD_PRELOAD` environment
and the game dies with *"failed to inherit capabilities: Operation not
permitted"* ([nixpkgs#351516](https://github.com/NixOS/nixpkgs/issues/351516)).
Normal priority beats not launching.

## Under the Hood

GE-Proton is declared through `extraCompatPackages` rather than installed with
ProtonUp. That pins it to nixpkgs — it updates on `nix flake update` like
everything else and rolls back with the generation. Slightly staler than
ProtonUp; enormously more boring, which is the trade this whole repo keeps
making.

`extest.enable` is a Wayland-specific fix worth naming, because the symptom is
so unhelpful: Steam Input's controller remapping drives games by synthesizing
X11 XTEST events. Those don't exist on Wayland, so remapped controls silently
do nothing in a native Wayland game. extest translates them to uinput.

Launchers — Lutris, Heroic, Bottles — are named in a comment and left
uninstalled. Each is a large closure, and there is no non-Steam game to run
yet.

### The unrelated three

`python3`, `bc` and `file` went into `systemPackages` in the same pass. They
have nothing to do with games; they're all the same observation, which is that
**ad-hoc scripts assume a baseline that NixOS doesn't ship**. `uv` manages
project environments and can even fetch its own interpreters, but puts no plain
`python3` on `PATH`. `gawk` covers everything `bc` does and is guaranteed
present — but `bc` is what fingers type. And `file` is the nastiest of the
three, because its absence isn't an error:

```bash
find . -exec file {} \; | grep -v text     # no file(1) → empty output
```

Which reads as "no binary files here," not as "that command didn't run."

## What's Next

The `hosts/hypr-nix/` directory now has three optional imports —
`crash-diagnostics.nix`, `gaming.nix`, and the machine-specific
`hardware-sys76.nix` — each removable by deleting one line. That shape is
holding up well and is probably how anything else discretionary should land.

The open question is whether 32-bit audio's rebuild cost becomes annoying
enough in practice to be worth revisiting. It's now easy to measure: the whole
cost is attached to one import.
