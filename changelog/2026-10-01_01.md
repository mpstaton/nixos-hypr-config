# You Are Already on Latest: Two Meanings of Up-To-Date

## Why Care?

The machine had sat for a few weeks and felt stale, so the ask was the obvious
one: get everything to the latest release. The obvious follow-up question —
*what is the next NixOS release?* — turned out to have an answer that reframed
the whole job.

There isn't one yet. nixpkgs has no `nixos-26.11` branch. Releases are cut on a
May/November cadence and the branch only appears a few weeks ahead of ship, so
**26.05 was already the newest release**, and this laptop was pinned to it.

That matters because "out of date" had been doing two jobs in one phrase:

- **Behind on backports.** Real, and fixable in one command. `nixpkgs` and
  `home-manager` were locked at September 5th; both branches had moved to
  September 30th. Twenty-five days of security and point releases.
- **Behind on upstream.** Also real, but *unfixable by any release channel* —
  because the thing moving faster than 26.05 is not the next NixOS, it's the
  tools themselves.

## What the second one actually cost

`claude-code` had shipped **62 patch releases** in the 25 days stable sat still.
`flyctl` had shipped 56. A deploy CLI that far behind the server API it talks to
doesn't announce itself; it fails confusingly, later.

The tempting fix is to move the whole machine to `nixos-unstable`. That was the
wrong trade *here*, for two reasons specific to this laptop:

- `hardware-sys76.nix` runs the RTX 4070 in PRIME offload. Kernel and NVIDIA
  churn is the most common way that arrangement breaks, and it breaks at **boot**
   — where the cost is a rollback from the systemd-boot menu, not a retry.
- `gaming.nix` drags the 32-bit Steam stack, whose Hydra coverage is already
  thin enough to miss the cache (documented in this README since 2026-09-06).
  A rolling channel makes that more frequent, not less.

## What landed instead

A second nixpkgs input, exposed by an overlay as `pkgs.unstable.<name>`. Stable
keeps everything that boots the machine; the overlay takes the things that merely
run on it. Seventeen packages moved, prefix-by-prefix, in the three module files
that already listed them.

Because `home-manager.useGlobalPkgs = true`, home-manager shares the system
`pkgs` — so one overlay declared in `configuration.nix` resolves in `home.nix`
and `dev-tools.nix` with no further wiring. Three modules, one mechanism.

## The part worth stealing: measure before you overlay

The cherry-pick list was chosen from a version diff of both channels, not from
instinct. That immediately killed a third of the candidates:

| Verdict | Packages |
|---------|----------|
| **Identical in both channels** | `gh` 2.102.0, `helix` 25.07.1, `delta`, `lazydocker`, `nodejs_24` 24.21.0, `zellij` 0.45.1 |
| **Delta too small to pay for** | `neovim` 0.12.4→0.12.5, `ripgrep` 15.1.0→15.2.0 |

Overlaying any of those would have added a parallel dependency tree in exchange
for nothing. That isn't a hypothetical cost — unstable's glibc is not 26.05's,
and you can watch it happen in the build log, which fetches `nghttp2-1.68.1` and
`nghttp2-1.70.0` side by side, one per channel. Nix is built for that and
handles it correctly. It is still disk and download, and it is the entire reason
this list is short CLI tools and not browsers or anything Electron-sized.

## Three majors, taken on purpose

`surrealdb` 2.6.1→3.0.0, `pnpm` 11.27.0→12.3.4, `railway` 4.36.1→5.30.4 were
flagged as decisions rather than freebies, and taken deliberately. Two things
checked first turned the scariest one from a risk into an argument *for* going:

- **There is no local SurrealDB data on this machine** — no `~/.surrealdb`, no
  `*.surql`, no surreal unit, no surreal container. The storage-format migration
  that makes a database major frightening had nothing here to migrate.
- **`surrealist` was already 3.6.1 on both channels.** The stable 2.6.1 *server*
  was the mismatched half. The bump aligned them rather than splitting them.

`pnpm` 12 and `railway` 5 carry deferred rather than immediate risk: a switch
only puts a binary on PATH. pnpm's lockfile change bites on the next
`pnpm install`, in a git-tracked tree, at a time of choosing.

## Still outstanding

`hunk` pins its *own* nested nixpkgs — `nixos-unstable` at **2026-05-05**, five
months stale — and bumping the `hunk` input doesn't move it, because that pin
lives in hunk's own lockfile. It's a third nixpkgs in the evaluation. Now that
this flake has a `nixpkgs-unstable` input, `hunk.inputs.nixpkgs.follows` could
collapse it; the existing comment warns that hunk's bun2nix build wants its own
pin, so that's a separate experiment with its own verification, not a drive-by.
