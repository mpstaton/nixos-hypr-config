# Splitting the Update: Run Everything Else First, Then Change What Boots

## Why Care?

On NixOS, `nix flake update` looks like a single safe command. But one lockfile
can mix two very different kinds of change. Some inputs only change programs that
**run on** the machine: a browser, a CLI, a home-manager module. One input changes
what **boots** it: the kernel, the GPU driver, systemd and glibc. If you update them
together and something breaks, you can't tell which kind of change caused it.

That happened here. The autoupdater bumped every input at once, and the machine
crashed right after the build finished, before anything was activated. We never
found out which part was to blame, and as far as we know the timing may have been
a coincidence. Both are reasons to do it in a way that doesn't need an answer.

## What's New?

The same update, split into two commits and checked at each step:

| Step | Commit | Inputs moved | Checked by |
|------|--------|--------------|------------|
| 1. Doesn't touch boot | `3e3f03e` | `nixpkgs-unstable`, `zen-browser`, `hunk`, `home-manager` | `switch`, then using the machine |
| 2. Boot path | `9d583fe` | root `nixpkgs`: 26.05 snapshot `78e9c78` → `7c8764b` | `boot`, then a **reboot** |

Step 1 changed 9 packages, all user-facing tools (claude-code, zen-browser, pnpm, uv,
lazygit and others). Step 2 is the one covered here.

## What step 2 actually moved

`nvd diff` between generations 33 and 34, cut down to the parts that matter for booting:

| Package | Before | After |
|---------|--------|-------|
| `linux` (+ initrd) | 6.18.54 | 6.18.55 |
| `nvidia-open` | 595.71.05 built for 6.18.54 | same driver, rebuilt for 6.18.55 |
| `system76-module`, `system76-io-module` | built for 6.18.54 | rebuilt for 6.18.55 |
| `systemd` | 260.4 | 260.5 |
| `glibc` | 2.42-84 | 2.42-100 |
| `xwayland` | 24.1.13 | 24.1.14 |

Everything else was ordinary backports: Firefox 157.0.1, Brave, Docker/moby 29.8.1,
podman 5.8.8, kitty 0.49.1, webkitgtk 2.54.1, flatpak 1.18.4, wpa_supplicant 2.12,
and a Perl point release that rebuilt its module set.

The NVIDIA driver version didn't change. It was only rebuilt against the new kernel.
That's the best case for this laptop's PRIME offload setup: the biggest risk with
a kernel bump is the out-of-tree module, and here only its build target changed.

## How it was verified

Changes to the boot path aren't proven by `nixos-rebuild switch`. A running system
keeps its old kernel and the old systemd as PID 1. The only real test is booting
into it. After the reboot:

- **The machine booted generation 34.** `/run/booted-system` and
  `/run/current-system` both point to `26.05.20261008.7c8764b`, so systemd-boot
  didn't fall back to an older generation.
- **No failed units**, at system or user level. The `home-manager-mps` activation
  exited 0.
- **No coredumps** from this boot.
- **The desktop came up.** SDDM, then Hyprland 0.55.4, the portals, Bluetooth,
  NetworkManager, WirePlumber and the Portainer container.

The journal is still noisy, but it's the same noise as before the update: dbus
"duplicate name" warnings from having both KDE and Hyprland service files
installed, and GTK theme parse warnings. Nothing new appeared.

## What's Next

The split is now how we do it: update the inputs that don't touch boot and
`switch`, then update root `nixpkgs`, `boot` and reboot. A next step could be to
have the autoupdater do the first half on its own and leave the second for a
human who is around to reboot.

The crash during the all-at-once update is still unexplained. If it happens again
during step 1 of a future update, that rules out the boot path.
